# When a real-time voice companion should speak or stay silent during live gameplay — turn-taking, interruptions, backchannels and game-intensity gating

_Status: COMPLETE (final update 7, 2026-11-01; ~45 pages opened). Context: MapleSyrup, an observational PC voice companion for MapleStory (vision-only "syrup" engine, realtime voice model + Claude fallback after a spoken "let me think", 1 s → 0.5 s latency target, Hebrew + English, data-driven conversational content, no magic strings). All vendor numbers below are vendor-reported unless marked otherwise. Pages were opened via WebFetch; URL sits next to each claim._

## Key Question 1 — End-of-turn detection and turn-taking prediction (2025–2026 tools): accuracy, added latency, language support incl. Hebrew

### Takeaway
By mid-2026 the state of the art moved from "VAD silence timer" to small audio-native end-of-turn (EOT) classifiers that run in 10–60 ms on CPU and cut false cut-offs to ~5–10 % at 300–600 ms latency budgets (LiveKit v1, Pipecat Smart Turn v3.x, Deepgram Flux, AssemblyAI). None of the open or vendor EOT models opened so far lists Hebrew: LiveKit audio detector (14 languages), Smart Turn v3 (23 languages) and Deepgram Flux (English) all omit it, so for Hebrew MapleSyrup must either fall back to VAD + silence timers, use a realtime model's built-in semantic VAD (OpenAI/Gemini), or fine-tune an open model (Smart Turn is fully open: weights, data, training script).

### Cited Findings
**LiveKit turn detector**
- LiveKit's current turn detector is an *audio* model: it "encodes user audio directly, so it doesn't rely on a transcript" and combines what is said with intonation, pitch and rhythm; the older *text* turn detector (Qwen2.5-0.5B-Instruct on STT transcripts) is deprecated and slated for removal in SDK 2.0. — [LiveKit docs: Turn detector](https://docs.livekit.io/agents/logic/turns/turn-detector.md)
- Audio detector versions: `v1` (full model on LiveKit Inference, free for agents deployed on LiveKit Cloud) and `v1-mini` (runs locally on CPU, free anywhere). — [LiveKit docs](https://docs.livekit.io/agents/logic/turns/turn-detector.md)
- Audio detector languages (14): English, Arabic, German, Spanish, French, Hindi, Indonesian, Italian, Japanese, Korean, Dutch, Portuguese, Turkish, Chinese. Text detector (14): English, Spanish, French, German, Italian, Portuguese, Dutch, Chinese, Japanese, Korean, Indonesian, Turkish, Russian, Hindi. **Hebrew is in neither list.** — [LiveKit docs](https://docs.livekit.io/agents/logic/turns/turn-detector.md)
- Text model: 396 MB on disk, ~50–160 ms per turn on CPU, <500 MB RAM; per-language true-positive ≈99.3–99.4 %, true-negative 85.1 % (Italian) to 96.3 % (Hindi), English 99.3 % / 87.0 %. Audio model: no size/latency published in docs; if no prediction arrives within ~1 s the agent commits the turn anyway. — [LiveKit docs](https://docs.livekit.io/agents/logic/turns/turn-detector.md)
- The audio detector requires a VAD whose `min_silence_duration` ≥ 0.25 s (Silero default 0.55 s). `unlikely_threshold` sets how confident the model must be before a turn counts as complete (lower = more eager); can be a scalar or per-language dict. Endpointing `min_delay`/`max_delay` default 0.5 s / 3.0 s (0.3 s / 2.5 s with the audio detector); `mode` `fixed` or `dynamic` (adapts within min/max, `alpha` 0.9). — [LiveKit docs](https://docs.livekit.io/agents/logic/turns/turn-detector.md)
- LiveKit blog (2026-06-17) describing v1: a semantic branch (audio encoder → learned adapter → fine-tuned LLM, no transcript) plus an acoustic branch (encoder → recurrent layer for timing/prosody) and a fusion module; uses only the current user turn as context. Reported on their open **eot-bench**: at a 300 ms latency budget v1 has a 9.9 % false-cutoff rate vs 12.9 % for Deepgram Flux and 27.7 % for ultraVAD; at 600 ms, 4.5 % vs 5.5 % (Soniox) and 9.9 % (Deepgram Flux); at a 5 % false-cutoff target v1's mean latency is 543 ms, at 10 % it is 295 ms. Earlier versions "cut unwanted interruptions by 39 %" (baseline not stated). — [LiveKit blog: Solving end-of-turn detection](https://livekit.com/blog/solving-end-of-turn-detection)

**Pipecat Smart Turn (Daily)**
- Smart Turn v3 (2025-09-11): Whisper-Tiny encoder layers + classification head, 8 M parameters, 8 MB int8 ONNX; inference incl. preprocessing 12.6 ms on AWS c7a.2xlarge CPU, 3.3 ms on L40S GPU, 94.8 ms on t3.medium. Accepts up to 8 s of the current turn; "a VAD model like Silero should be used in conjunction with Smart Turn". Fully open (weights, training data, training script). — [Daily blog: Smart Turn v3](https://www.daily.co/blog/announcing-smart-turn-v3-with-cpu-inference-in-just-12ms/)
- Smart Turn v3 languages (23): Arabic, Bengali, Chinese, Danish, Dutch, German, English, Finnish, French, Hindi, Indonesian, Italian, Japanese, Korean, Marathi, Norwegian, Polish, Portuguese, Russian, Spanish, Turkish, Ukrainian, Vietnamese. **Hebrew not included.** Per-language test accuracy ranges 97.1 % (Turkish) to 81.3 % (Vietnamese); English 94.31 % (FP 2.64 %, FN 3.06 %, n=2,846). — [Daily blog: Smart Turn v3](https://www.daily.co/blog/announcing-smart-turn-v3-with-cpu-inference-in-just-12ms/)
- Smart Turn v3.1 (2025-12-03): same architecture, more human data (English/Spanish); on the v3.1 test set English rose 88.3 % → 94.7 % (8 MB CPU) / 95.6 % (32 MB GPU), Spanish 86.7 % → 90.1 % / 91.0 %. Latency 8 MB model: 2 ms L40S, 9 ms c7a.2xlarge CPU, 57 ms c8g.medium CPU (+7–9 ms preprocessing); ~70 ms on Pipecat Cloud. — [Daily blog: Smart Turn v3.1](https://www.daily.co/blog/improved-accuracy-in-smart-turn-v3-1/)

**Deepgram Flux**
- Flux (launched 2025-10-01) is a "Conversational Speech Recognition" model where the same model that transcribes also detects turn ends (replacing separate ASR + VAD + endpointing). Events: `StartOfTurn`, `EndOfTurn`; config `eot_threshold` (default 0.7) and `eot_silence_threshold_ms` (default 5000 ms, silence fallback). Claimed 200–600 ms lower agent response latency than pipelines, EndOfTurn within 1.5 s 95 % of the time, p90 ≈1 s, ~30 % fewer false interruptions; optional eager mode: `eager_eot_threshold` (0.3–0.5) emits `EagerEndOfTurn` ~150–250 ms before `EndOfTurn` for speculative LLM calls, with `TurnResumed` to cancel — at the cost of 50–70 % more LLM calls. Roadmap lists "extending CSR beyond English", implying English-only at launch. — [Deepgram blog: Introducing Flux](https://deepgram.com/learn/introducing-flux-conversational-speech-recognition)

**AssemblyAI Universal-Streaming**
- End-of-turn detection is built into the streaming STT model and combines a semantic/acoustic EOT prediction with a silence heuristic; either can trigger. Parameters: `end_of_turn_confidence_threshold` (default 0.7; 1 disables model-based EOT), `min_end_of_turn_silence_when_confident` (default 160 ms), `max_turn_silence` (default 2400 ms); both triggers need ≥80 ms of speech since the last EOT; a `ForceEndpoint` message lets your own VAD force a turn end. No latency/accuracy figures and no language list on this page. — [AssemblyAI docs: Turn detection](https://www.assemblyai.com/docs/speech-to-text/universal-streaming/turn-detection)

**OpenAI Realtime API VAD**
- `server_vad` (default for speech-to-speech): `threshold` (0–1), `prefix_padding_ms`, `silence_duration_ms`, plus `create_response` / `interrupt_response` (speech-to-speech only). `semantic_vad`: a classifier scores the probability the user has finished based on their words; low probability → longer wait, high → little or no wait; `eagerness` ∈ {`low`, `medium`, `high`, `auto`} (auto = medium) tunes the maximum wait timeout; actual timeout values are not published. Turn detection can be disabled (`null`) and audio committed with `input_audio_buffer.commit`. — [OpenAI docs: Realtime VAD](https://developers.openai.com/api/docs/guides/realtime-vad)

**Gemini Live API VAD**
- Automatic VAD on by default under `realtimeInputConfig.automaticActivityDetection` with `disabled`, `start_of_speech_sensitivity` (e.g. `START_SENSITIVITY_LOW`), `end_of_speech_sensitivity` (e.g. `END_SENSITIVITY_LOW`), `prefix_padding_ms`, `silence_duration_ms` (recommended 500–800 ms, server default ≈800 ms; 100–200 ms splits utterances, 2000 ms+ adds latency). Manual mode: `disabled: true` + client `activityStart`/`activityEnd`; hybrid: keep server VAD and send `audioStreamEnd` when client VAD ends. — [Gemini Live API capabilities guide](https://ai.google.dev/gemini-api/docs/live-api/capabilities)

**Voice Activity Projection (VAP) — academic lineage (foundational, 2022–2024)**
- Ekstedt & Skantze (Interspeech 2022) define VAP as "a general, self-supervised objective" for turn-taking that models dependencies between voice-activity events inside the projection window, with four zero-shot tasks on upcoming turn-shifts and backchannels; claims to outperform prior work. — [ISCA Archive: Ekstedt & Skantze 2022](https://www.isca-archive.org/interspeech_2022/ekstedt22_interspeech.html)
- Real-time VAP (Inoue et al., arXiv 2401.04868): CPC audio encoder → per-speaker self-attention transformer → cross-attention transformer; predicts both speakers' voice activity over the next 2 s as one of 256 joint states, with `p_now` (0–600 ms) and `p_future` (600–2000 ms); 50 frames/s; with ~1 s of context, balanced accuracy ≈76 % on shift-vs-hold at mutual silences >0.25 s, 14.6 ms per frame on an Intel Xeon CPU (real-time factor 0.73); trained/evaluated on English Switchboard, Japanese Travel Agency dialogues (92.5 h) and Mandarin HKUST; intended to replace fixed silence timeouts for deciding when the system takes its turn; backchannel timing not evaluated. — [arXiv 2401.04868](https://arxiv.org/html/2401.04868v1)

**Human timing norms (foundational, 2009–2015) — the target the tools are chasing**
- Stivers et al. (PNAS 2009), 10 languages: universal "avoidance of overlapping talk and a minimization of silence between conversational turns"; cross-language mean gaps differ within a range of 250 ms of the overall mean. — [MPI page for Stivers et al. 2009](https://forms.mpi.nl/node/50939)
- Levinson & Torreira (Frontiers in Psychology 2015), Switchboard subset of 348 conversations (~38 h): gaps "average around 200 ms"; "the great proportion of turn transitions fall between -100 and 500 ms"; single-word production takes ≈600 ms and simple sentences ≈1500 ms from stimulus to speech, so human listeners must begin planning their reply before the incoming turn ends. — [Frontiers: Levinson & Torreira 2015](https://www.frontiersin.org/articles/10.3389/fpsyg.2015.00731/full)

**Open path to Hebrew EOT**
- Smart Turn (GitHub, now v3.2): BSD-2-Clause; all training code in `train.py` (local or Modal via `train_modal.py`), datasets `pipecat-ai/smart-turn-data-v3.2-train/-test` on Hugging Face, modifiable to your own data; input 16 kHz mono PCM, up to 8 s (shorter padded at the start, longer truncated from the start); community data via turn-training games and `docs/data_generation_contribution_guide.md`; "Support for additional languages" is only a medium-term goal and Hebrew is not mentioned. — [GitHub: pipecat-ai/smart-turn](https://github.com/pipecat-ai/smart-turn)
- Hebrew real-time STT exists (e.g., Soniox `stt-rt-v5`, which streams Hebrew transcripts word by word and translates "as it is spoken"; 60+ languages; no endpointing/turn-detection feature described on the page; $0.18/hour in the pricing calculator) — so a Hebrew cascade would have to pair a Hebrew STT with a language-agnostic acoustic EOT or VAD. — [Soniox: Hebrew speech translation](https://soniox.com/speech-translation/hebrew)

### Inferences
- For MapleSyrup's 1 s → 0.5 s target, the EOT stage can realistically be budgeted at ~300–550 ms (LiveKit's 295 ms @10 % false-cutoff / 543 ms @5 %), which means the rest of the pipeline (LLM first token + TTS first audio) has to fit in ~450–700 ms; this is why speculative "eager" EOT (Deepgram `EagerEndOfTurn`) exists — it trades 50–70 % extra LLM calls for 150–250 ms.
- Hebrew is the critical gap: every dedicated EOT model opened lacks it. Options: (a) rely on the realtime model's own VAD (OpenAI `semantic_vad`, Gemini VAD — Gemini lists Hebrew `he` as a supported Live language); (b) fine-tune Smart Turn v3.2 with Hebrew data (BSD-2 licence, `train.py`, 8 s / 16 kHz clips labelled complete/incomplete — a few thousand Hebrew gameplay-style utterances recorded by the founder's community would mirror the per-language test-set sizes of ~800–1,400 in v3); (c) a conservative VAD + per-language silence timer for Hebrew with a longer `max_delay`. Note the acoustic branch of these models (prosody/intonation) is partly language-agnostic, so a Hebrew fine-tune starts from a strong prior.
- The human norm (~200 ms gap, most transitions −100…+500 ms) means even the 0.5 s target is at the slow edge of natural; the practical consequence is that the companion must start planning while the player is still speaking (speculative EOT / eager responses), exactly as humans do per Levinson & Torreira.
- Because gameplay has frequent mid-sentence pauses ("wait… [dodge]… so where do I go"), MapleSyrup should prefer models that explicitly handle "trailing-off" (OpenAI semantic VAD, AssemblyAI confident-vs-silence split) and set `max_turn_silence`-style fallbacks long (≥2 s), accepting slower responses on incomplete sentences over false cut-offs.

### Gaps
- No published Hebrew accuracy for any EOT model; AssemblyAI's and OpenAI's language coverage for turn detection was not stated on the pages opened.
- LiveKit's audio model size/latency not published in docs (only benchmark latencies at fixed false-cutoff targets).
- Independent (non-vendor) comparisons: LiveKit's eot-bench is open but vendor-run; no third-party replication found yet.

## Key Question 2 — Full-duplex speech models: backchannel / interrupt / self-initiate; maturity, availability, Hebrew

### Takeaway
Full-duplex models (Moshi 2024, PersonaPlex Jan 2026) achieve 170–260 ms turn latency and emit backchannels natively, but benchmarks show they over-take the floor during pauses (Moshi TOR ≈0.98) and — critically for MapleSyrup — a Sept-2026 study finds they initiate speech only when addressed or when silence occurs, almost never because content demands it. They are English-only in practice and GPU-class (7 B). Proactivity therefore has to come from an external policy/controller (RESPOND, CleanS2S-style), not from the speech model.

### Cited Findings
- **Kyutai Moshi** (arXiv 2410.00037, v1 2024-09-17, v2 2024-10-02): "the first real-time full-duplex spoken large language model"; models its own speech and the user's speech as separate parallel streams, removing explicit speaker turns and handling overlap, interruptions and interjections; "Inner Monologue" predicts time-aligned text tokens before audio tokens; theoretical latency 160 ms, ~200 ms in practice. The abstract page does not state language, model size or codec frame rate. — [arXiv 2410.00037](https://arxiv.org/abs/2410.00037)
- **NVIDIA PersonaPlex** (ADLR, published 2026-01-15): 7 B-parameter full-duplex model built on Kyutai's Moshi architecture (Mimi codec, temporal + depth transformers, Helium LM), 24 kHz dual-stream so it listens and speaks at once; it "learns timing behaviors: when to pause, interrupt, or backchannel (e.g., 'oh okay,' 'yeah')". Hybrid prompting: a voice-prompt audio embedding plus a natural-language role/context text prompt. — [NVIDIA Research: PersonaPlex](https://research.nvidia.com/labs/adlr/personaplex)
- PersonaPlex benchmarks (Full-Duplex-Bench, %): Smooth turn-taking 90.8 (Moshi 94.1, Gemini Live 65.5), User interruption 95.0 (Moshi 100.0, Gemini Live 89.1), Pause handling 60.6 (Moshi 1.8, Gemini Live 71.8). Response latency (s): PersonaPlex 0.170 smooth-turn / 0.240 interruption; Moshi 0.265 / 0.257; Gemini Live 1.301 / 1.183; Freeze-Omni 0.953 / 1.409. Task adherence (GPT-4o judge 0–5): PersonaPlex 4.29 / 4.40 vs Moshi 0.77 / 1.75. — [NVIDIA Research: PersonaPlex](https://research.nvidia.com/labs/adlr/personaplex)
- PersonaPlex training data is English (Fisher English 1,217 h + synthetic assistant 410 h + customer-service 1,840 h, TTS via Chatterbox); the page never states language support, examples are English. Code MIT, weights under NVIDIA Open Model License, base Moshi CC-BY-4.0; weights on Hugging Face `nvidia/personaplex-7b-v1`, code `NVIDIA/personaplex`. The page does not describe the model initiating speech unprompted beyond turn-taking behaviour. — [NVIDIA Research: PersonaPlex](https://research.nvidia.com/labs/adlr/personaplex)
- **Meta/UW SyncLLM** (EMNLP 2024, arXiv 2409.15594): Llama3-8b-based spoken dialogue model that "integrate[s] time information" to run synchronously with the real-world clock; trained on ≈212k hours of synthetic spoken dialogue (from text dialogues) + ≈2k hours of real dialogue; evaluated in a two-agent simulation tolerating up to 240 ms Internet latency; claims better dialogue meaningfulness at comparable naturalness. Abstract page does not state language, latency or weight release. — [arXiv 2409.15594](https://arxiv.org/abs/2409.15594v1)
- **Full-Duplex-Bench** (arXiv 2503.04721v3, 2025-08-16) measures four turn-taking skills: pause handling (Takeover Rate, lower better), backchanneling (TOR, backchannel frequency/s when TOR=0, Jensen-Shannon divergence vs human timing), smooth turn-taking (TOR + response latency), user interruption (TOR, GPT-4o quality 0–5, latency). Results: pause-handling TOR dGSLM 0.934, Moshi 0.985, Freeze-Omni 0.642, Gemini Live 0.255 (i.e., Moshi talks over almost every mid-turn pause; Gemini Live stays quiet most of the time); backchannel TOR Moshi 1.000 vs Gemini Live 0.091 (Gemini best JSD 0.896); turn-taking latency Moshi 0.265 s, dGSLM 0.352 s, Freeze-Omni 0.953 s, Gemini Live 1.301 s; interruption quality Freeze-Omni 3.615, Gemini Live 3.376, Moshi 0.765. The paper does not evaluate proactive initiation. — [arXiv 2503.04721v3](https://arxiv.org/html/2503.04721v3)
- **"Full-Duplex Speech Models Take the Floor When Asked, Not When Needed"** (Peng, Nuchged, Fu, Yao; arXiv 2609.19596, submitted 2026-09): 40 English monologues × 10 trigger conditions (Question, Request, Rhetorical, Word search, False fact, Repeat, Hazard, Turn end, Silence, Neutral); metric = speech-onset rate (≥4 words within 4 s of trigger). Models: Moshi, Moshika-RL, PersonaPlex (PPlex), PPlex-RL, NVIDIA VoiceChat-11B, MiniCPM-o 4.5, Raon-SpeechChat. Onset rates — Moshi: Neutral .07, Question .15, False fact .08, Hazard .10, Silence .12; PPlex: .10 / .34 / .07 / .16 / .83; MiniCPM-o 4.5: .00 / .01 / .00 / .00 / .98; Raon-SpeechChat ≈.35–.68 everywhere (near-continuous talking). Rhetorical questions and "that's all from me" cues had almost no effect; explicit permission ("if I say anything wrong, please interrupt me") changed onset by ≤.05. When *given* the floor after 10 s silence, replies rarely addressed the problem: false-fact corrections .14 (Moshi) / .15 (PPlex), hazard warnings .04 / .07. Conclusion: current full-duplex models speak when addressed or when there is silence, not when content calls for intervention; "requires genuine content understanding and intervention decisions grounded in it." — [arXiv 2609.19596](https://arxiv.org/pdf/2609.19596)
- **RESPOND** (Microsoft + U. Houston, arXiv 2603.21682v2, 2026-03-30): a text-based listener module that at every word boundary predicts *turn claim* / *backchannel* / *stay silent* from streaming ASR (Azure) over ≤5 s windows, using Qwen3-0.6B + LoRA with two FiLM-injected scalar controls — Backchannel Intensity and Turn Claim Aggressiveness — adjustable without retraining. CANDOR (850 h video calls): F1 0.847 turn-claim, 0.845 backchannel, 0.902 silent, 87 % accuracy; MM-F2F text-only 75.6 %. ASR delay estimated 250–500 ms; end-to-end latency not measured. Six-person pilot: sentence-final backchannels felt natural, mid-sentence ones disruptive; frequent or mistimed turn claims reduced trust; most chose low turn-claim aggressiveness and moderate backchannel intensity. English datasets. — [arXiv 2603.21682v2](https://arxiv.org/html/2603.21682v2)
- **CleanS2S** (arXiv 2506.01268, 2025): cascaded ASR→LLM→TTS framework whose "proactive" behaviour is a fine-tuned *Subjective Action Judgement* LLM choosing among five strategies — input interruption, explicit refusal, deflective response, **non-response (silence)**, standard response — using a memory module (temporal signals, history, factual anchors); trained on interview/talk-show data with pause durations guiding annotation and truncated segments as negatives to curb indiscriminate interruption; judgement accuracy 0.84 → 0.91 after Action-Judgement SFT (Llama-3.1-8B). It does not describe unprompted initiation, and gives no latency numbers. — [arXiv 2506.01268](https://arxiv.org/html/2506.01268v1)
- **Kyutai Unmute** (2025-05-22): cascaded STT→LLM→TTS voice layer whose STT "includes a semantic VAD that predicts whether you've actually finished speaking", designed not to interrupt mid-sentence pauses; interruptible; streaming TTS starts before the LLM finishes; open-sourcing promised; no latency numbers or language list on the page. — [Kyutai: Unmute](https://kyutai.org/2025/05/22/unmute.html)

### Inferences
- Full-duplex models are the only architecture where backchannels ("yeah", "oh okay") and overlap emerge natively; cascaded/realtime APIs must fake them. But PersonaPlex/Moshi are English-only in practice and 7 B parameters (GPU-class), so they are not a drop-in for a Hebrew PC companion in 2026.
- The 2026 evidence is decisive on *initiative*: no shipped full-duplex model decides to speak because the *content* warrants it (false fact, hazard, word search) — they fire on being addressed or on silence (PPlex .83, MiniCPM-o .98 onset after silence vs ≤.16 on hazards). Therefore MapleSyrup's "intuition" cannot be delegated to the speech model; it must be an external *conversation director* that watches game state + dialogue state and injects utterances (the approach RESPOND and CleanS2S take with small text-side policy models, and which Gemini's `proactive_audio` only partially covers on the "stay silent" side).
- RESPOND's two scalar knobs (Backchannel Intensity, Turn Claim Aggressiveness) are a good data-driven interface: MapleSyrup can expose the same two scalars per player (and per game intensity level) rather than hard-coding behaviour.

### Gaps
- No full-duplex model with documented Hebrew support was found (Moshi/PersonaPlex/SyncLLM/VoiceChat/MiniCPM-o are English or English+Chinese in their papers). Gemini Live is the only realtime system listed with Hebrew that was also benchmarked on Full-Duplex-Bench (and it had the slowest latency, 1.3 s, in that 2025 run — likely improved since but no newer independent numbers found).

## Key Question 3 — Realtime voice APIs and proactivity: injecting an unsolicited utterance, choosing silence

### Takeaway
Both major realtime APIs let a backend make the model speak unprompted — OpenAI via `conversation.item.create` + `response.create` (optionally out-of-band with `conversation: "none"` and per-response `instructions`), Gemini via `send_client_content`/`send_realtime_input(text)` — and both let the backend take over turn control (`create_response: false` / `turn_detection: none`; Gemini manual `activityStart/End`). "Choosing silence" is native only in Gemini's `proactive_audio` (model may decide not to respond), with a flaky history and unclear support on the current 3.8 Live model; OpenAI offers only the idle-timeout nudge (`idle_timeout_ms` → `input_audio_buffer.timeout_triggered`) and ElevenLabs a `turn_timeout` re-prompt. A game companion therefore needs its own director deciding *when* to call `response.create`.

### Cited Findings
**Gemini Live API (Google AI for Developers, as read 2026-11-01)**
- Proactive audio: `proactivity={'proactive_audio': True}` (JS `proactivity: { proactiveAudio: true }`), requires `v1beta`; "When this feature is enabled, Gemini can proactively decide not to respond if the content is not relevant." Affective dialog: `enable_affective_dialog: true` — "lets Gemini adapt its response style to the input expression and tone." Both are marked **not supported in Gemini 3.1 Flash Live**; the page lists `gemini-3.8-live` as the default model and `gemini-3.8-live-extended-thinking` (thinkingLevel low/medium/high) and does not state whether 3.8 supports proactive audio. — [Gemini Live API capabilities guide](https://ai.google.dev/gemini-api/docs/live-api/capabilities)
- Hebrew (`he`) is listed as a supported Live API language; native-audio models auto-detect language and can be restricted through system instructions. Audio-only sessions limited to 15 min (audio+video 2 min) without session-management techniques; 128k-token context for native-audio-output models. — [Gemini Live API capabilities guide](https://ai.google.dev/gemini-api/docs/live-api/capabilities)
- Injecting an unsolicited utterance: `send_realtime_input(text=...)` for simple text, or `send_client_content` with `user`/`model` turns and `turn_complete` — setting `turn_complete=true` interrupts ongoing generation; works throughout the session. Interruptions: when VAD detects barge-in, generation is cancelled, `server_content.interrupted` is set, pending function calls are discarded and their IDs reported; the client must stop playback and flush queued audio. — [Gemini Live API capabilities guide](https://ai.google.dev/gemini-api/docs/live-api/capabilities)
- The Vertex AI Live API overview (as read 2026-11-01) lists models "3.8 Live", "2.5 Flash Live API" and "3.5 Live Translate" and a migration page "Migrate from Gemini 2.5 Flash Live API to Gemini 3.8 Live". — [Vertex AI: Gemini Live API overview](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/live-api)

**OpenAI Realtime API**
- `create_response` and `interrupt_response` flags on `server_vad` govern whether VAD-detected turns auto-create responses and whether user speech interrupts an ongoing response (speech-to-speech only). — [OpenAI docs: Realtime VAD](https://developers.openai.com/api/docs/guides/realtime-vad)
- Idle nudge: set `idle_timeout_ms` under `turn_detection` (`type: server_vad`, example 6000 ms) via `session.update`; the timer starts after the last model response's audio finishes playing; if VAD does not fire in that window the server sends `input_audio_buffer.timeout_triggered`, which "commits an empty audio segment to conversation history and triggers a model response" — intended to let the model check whether VAD missed an utterance or say something like "Are you still there?". Context `truncation` with `type: retention_ratio` (e.g. 0.8) drops 20 % of context at the limit to preserve prompt caching. GA model `gpt-realtime` (blog 2025-09-12; `gpt-realtime-2025-08-28` for EU residency). — [OpenAI Developers blog: Developer notes on the Realtime API](https://developers.openai.com/blog/realtime-api)
- Manual/unsolicited speech on OpenAI Realtime (Azure OpenAI how-to, same protocol): `turn_detection.type` ∈ {`none`, `semantic_vad`, `server_vad`} (default `server_vad`); with `create_response: false` VAD still detects end of speech but "the server doesn't generate a response until you send a `response.create` event"; with `none` you push-to-talk via `input_audio_buffer.commit` + `response.create`. Out-of-band responses: "By default, responses generated during a session are added to the default conversation state" — set `response.conversation: "none"` to generate outside it, with `metadata` echoed back in `response.done` and an `input` array of `item_reference`s and/or new `message` items for custom context; per-response `instructions` can be passed in `response.create`. ## Key Question 4 — HCI evidence on interruptibility and attention-aware timing (Horvitz, breakpoints, cognitive load, games/driving)

### Takeaway
The canonical framework is Horvitz's expected-utility decision between act / ask / stay silent with thresholds that rise when the user is deeply focused, plus the breakpoint literature showing that deferring non-urgent messages to task boundaries (medium/coarse breakpoints) lowers frustration and speeds reaction — directly transferable to a companion deciding when to voice a thought.

### Cited Findings
- Horvitz (CHI 1999) 12 principles of mixed-initiative UI include: considering uncertainty about the user's goals; considering the status of the user's attention and "timing services and alerts to the user's attention, deferring when action would be distracting"; inferring the ideal action under uncertainty (weighing context-dependent costs/benefits); employing dialog to resolve key uncertainties; minimizing the cost of poor guesses (timeouts, cheap rejection gestures); scoping precision to uncertainty ("do less, but do it correctly"); and maintaining working memory of recent interactions. — [Horvitz, Principles of Mixed-Initiative User Interfaces (PDF)](https://erichorvitz.com/chi99horvitz.pdf)
- Horvitz formalizes the choice: eu(A|E) = p(G|E)·u(A,G) + [1−p(G|E)]·u(A,¬G) vs eu(¬A|E); adding dialog yields two thresholds p*(¬A,D) (do nothing vs ask) and p*(D,A) (ask vs act). "Deep focus on another task lowers the utility of unwanted action, raising the threshold. Being rushed lowers the utility of missed action, reducing the threshold." LookOut used a sigmoid dwell-time model in message length to defer offers until the user is likely ready. — [Horvitz 1999 (PDF)](https://erichorvitz.com/chi99horvitz.pdf)
- Iqbal & Bailey (CHI 2008): a breakpoint is "a transition between two observable, meaningful units of task execution" at Coarse/Medium/Fine granularity; their OASIS system defers notifications to the next breakpoint with a max wait. In a 16-user study, relevant notifications delivered at breakpoints were reacted to faster (3.07 s vs 4.08 s immediate, p<0.056); in diagram editing, frustration was lower at Medium breakpoints (2.6) than Fine (5.5) or Immediate (4.5), with Coarse at 3.6; general-interest notifications caused more frustration (4.98) than relevant ones (3.59); users wanted relevant notifications at Medium/Fine breakpoints and general-interest ones at Coarse; mean deferral 88.6 s was judged acceptable; 64 % of scheduled deliveries landed on moments users agreed were breakpoints. Their breakpoint-detection models generalized poorly to new users/tasks (recall 41.5 % coarse / 20.4 % medium / 15 % fine in programming), so the authors recommend using them for detection rather than type differentiation. — [Iqbal & Bailey CHI 2008 (PDF)](https://www.interruptions.net/literature/Iqbal-CHI08.pdf)
- Kim et al. (UbiComp/ISWC 2019 adjunct, "Predicting Opportune Moments for In-vehicle Proactive Speech Services"): defined driver interruptibility along three dimensions — driving safety, auditory-verbal task performance, perceived difficulty; 29 drivers, 1,388 labelled cases (939 interruptible / 449 not); 171 features from OBD-II + dashcam (steering angle, speed, manoeuvre type, distance to nearby cars, traffic) over 1–5 s windows; Random Forest F-measure 0.74 at a 2-second window (>0.70 across windows); user-specific models ≈0.71, similar to the general model; implication: use the model to decide when system-initiated speech is delivered and to limit user-initiated interaction when classified uninterruptible. — [Kim et al. 2019 (PDF)](https://ic.kaist.ac.kr/files/papers/kim2019predicting.pdf)
- ProVoice (CHI 2026, arXiv 2601.19421): human-in-the-loop multi-objective Bayesian optimisation of proactive in-vehicle assistant interventions (19 participants, VR driving sim) over glow, alert volume, symbol transparency and Level of Autonomy, minimising NASA-TLX mental demand and maximising predictability/usefulness; predictability and usefulness correlated positively (r = 0.47), mental demand and usefulness negatively (r = −0.32); the trained autonomy level converged near Level 3 (mean 0.634). Design guidance: interventions should account for driver availability because stress and workload rise before complex manoeuvres; higher autonomy in volatile high-speed driving, lower when stationary. No timing windows or frequency thresholds are given. — [arXiv 2601.19421](https://arxiv.org/pdf/2601.19421)
- Hsieh et al., CHI 2020 (VR notifications; the closest controlled game-interruption study found): 40 participants, four activities × 3 notifications each; engagement (7-pt) Rhythm Game 6.54, Treasure Hunt 5.87, 360 Video 4.78, Loading 4.18; perceived disruptiveness rose with engagement — Rhythm Game 5.56, Treasure Hunt 3.71, 360 Video 2.71, Loading 1.61; perceived timeliness was best during Loading (6.51) and worst during the Rhythm Game (2.30); recall was significantly lower in both games, and in the rhythm game players confused game vibration with notification vibration. Implications: defer non-urgent notifications during high engagement and find breakpoints; use a peripheral unread indicator rather than full content; keep notification modality distinct from game feedback. — [Hsieh et al. CHI 2020 (PDF)](https://people.cs.nycu.edu.tw/~armuro/pubs/hsieh-et-al-2020-chi.pdf)
- US patent 12,168,175 ("Method and system for automatically controlling user interruption during game play of a video game"; assignee not visible in the text read): a per-player machine-learned model estimates "a level of immersion" from game-state data (objects, character attributes, overlays), telemetry, controller input, motion and biometrics (heart rate, sweat, voice loudness), given a detected gaming context such as a boss fight or weapon change; "the threshold is determined based on a skill level of the player and the gaming context"; above threshold an indicator signals "the player should not be interrupted" and third-party communications can be blocked; player feedback on prediction correctness retrains the model. — [USPTO full text (PDF)](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/12168175)

### Inferences
- Map Horvitz onto the conversation director: p(G|E) = probability the player would welcome this utterance now; u(A,¬G) = cost of unwanted speech (very negative in a boss fight, mild while travelling); the "ask" middle band corresponds to a short, interruptible teaser ("want a tip?") rather than a monologue. Attention status = inferred game intensity.
- Breakpoints in MapleStory are observable through syrup: end of a mob pack, map/portal change, arrival in town, opening a menu/shop, death/respawn, quest-complete banner, loading screens. Proactive small talk belongs at Medium/Coarse breakpoints (map change, town arrival); game-relevant tips at Fine breakpoints (between mob packs); alerts (HP) immediately.

### Gaps
- No study found that measures interruption cost specifically during PC/MMO combat; the VR-notification study (Hsieh 2020: disruptiveness 5.56 in a rhythm game vs 1.61 while loading) and the driving literature are the closest analogues; Kim et al. do not report *which* driving contexts were interruptible, only that interruptibility is predictable from sensors (F≈0.74).


## Key Question 5 — Game-design practice for pacing companion chatter (Valve AI Director, Ruskin's dynamic dialog, companion barks, cooldowns)

### Takeaway
Valve's data-driven "rule database" (Ruskin, GDC 2012) is the closest existing blueprint to MapleSyrup's requirement for content that is pure data: a flat fact query (concept, who, map, HP, counters…), rules whose criteria must all pass with most-specific-rule-wins, responses with random variants, "then" clauses that write back memory facts with automatic expiry (the cooldown mechanism), random-chance criteria to throttle over-played lines, and re-querying at callback time so follow-ups silently die when the situation changed.

### Cited Findings
- Ruskin (Valve, GDC 2012 "AI-driven Dynamic Dialog through Fuzzy Pattern Matching"): world state is **facts** (key-value, e.g. "current map is swamp", "hitpoints are 57"); a **query** is a flat associative array merging speaker facts, the speaker's persistent memory and world state, and must include `concept` (e.g. "saw enemy") and `who`; a **criterion** is one true/false test on a fact stored as an interval; a **rule** is a set of criteria that must all pass (and rejects if a referenced fact is missing); a **response** can hold several variations picked at random. — [GDC 2012 slides (PDF)](https://cdn.fastly.steamstatic.com/apps/valve/2012/GDC2012_Ruskin_Elan_DynamicDialog.pdf)
- Best match = the matching rule with the most criteria ("most specific rule wins"), which the slides say worked better than weighted alternatives; ties broken randomly for variety. — [GDC 2012 slides](https://cdn.fastly.steamstatic.com/apps/valve/2012/GDC2012_Ruskin_Elan_DynamicDialog.pdf)
- Memory/cooldown: "then" clauses write facts back to the speaker or world (e.g. "line was played"), appended to later queries so a second sighting gets a different line; facts can have **automatic expiration times** — e.g. a "speaking" flag that lapses after a few seconds to keep running gags from firing too close together. Speak-once is "line hasn't been said" criterion + memory flag (slides say a self-removing response would have been better). Over-chatter is throttled with a random-chance criterion (e.g. "random number less than 30"). — [GDC 2012 slides](https://cdn.fastly.steamstatic.com/apps/valve/2012/GDC2012_Ruskin_Elan_DynamicDialog.pdf)
- Follow-ups/conversations: a "then" clause sends a follow-up concept to a character (or all nearby) when the line finishes; the follow-up is queried when the callback fires, not when the first line starts — if a zombie appears mid-conversation the "not in danger" criterion fails and the conversation ends "without any explicit interruption logic"; long monologues are split into chained lines so they can be cut short. Scale: Left 4 Dead series >10,000 lines; bucketing by speaker/concept/map gives ~50 rules per bucket, avg 8 criteria per rule, lookups <1 µs. The slides mention the L4D Director as a separate pacing system but do not describe it gating speech. — [GDC 2012 slides](https://cdn.fastly.steamstatic.com/apps/valve/2012/GDC2012_Ruskin_Elan_DynamicDialog.pdf)

**Valve AI Director (Left 4 Dead) — foundational 2009 material**
- Mike Booth (Valve, GDC 2009 "The AI Systems of Left 4 Dead"): per-Survivor **Intensity** rises on injury (scaled to damage taken), incapacitation, being pulled/pushed off a ledge, and nearby Infected dying (scaled inversely with distance); it decays toward zero over time, with decay suspended while Infected actively engage that Survivor; the Director tracks the highest intensity among the four Survivors. — [Booth 2009 slides (PDF)](https://steamcdn-a.akamaihd.net/apps/valve/2009/ai_systems_of_l4d_mike_booth.pdf)
- Director cycle: **Build Up** (full threat population until intensity crosses a peak threshold) → **Sustain Peak** (full population "3-5 seconds after Survivor Intensity has peaked") → **Peak Fade** (minimal population until intensity decays below the peak range; won't enter Relax until a natural break in combat) → **Relax** (minimal population for 30-45 seconds or until the team has moved far enough toward the next safe room) → Build Up. Mobs spawn every 90-180 s on Normal. "Amplitude (difficulty) is not changed, frequency (pacing) is." The slides do not describe music or dialogue being driven by intensity, and give no numeric intensity/decay constants. — [Booth 2009 slides (PDF)](https://steamcdn-a.akamaihd.net/apps/valve/2009/ai_systems_of_l4d_mike_booth.pdf)

**Alien: Isolation (Creative Assembly) — second "director" example**
- The Director tracks a "menace gauge" that rises when the alien is within short walking distance, when the player has line of sight to it, and when it is close on the motion tracker and can reach the player quickly (slower rise if it is in another room); when menace peaks, the Director pulls the alien back to neighbouring areas or into the vents "to stop players from becoming overwhelmed"; Andy Bray (CA, nucl.ai 2016): players "can't be kept scared all the time, or they'll give up, so tension has to vary." No numeric thresholds or timers are given. — [Game Developer: The Perfect Organism — the AI of Alien: Isolation](https://www.gamedeveloper.com/design/the-perfect-organism-the-ai-of-alien-isolation)

**Hades (Supergiant)**
- Secondary analysis of Hades' dialogue: each hub NPC has 200–600+ unique lines tagged with trigger conditions from run events (dying to a specific boss N times, carrying N boons of a god, gifting an item, first biome clear); "most lines fire once and never again"; each NPC also has a background pool of repeating filler lines that fill silence between unique-line triggers; Hades 2 forks trigger pools by path. The page does not describe priority ordering or cooldowns and cites no source for its ~21,000-line figure, so treat it as secondary. — [saschb2b: Hades — death as narrative](https://saschb2b.github.io/game-mechanics/games/hades/death-as-narrative)
- Supergiant's GDC 2021 talk "Breathing Life into Greek Myth: The Dialogue of Hades" (Kasavin & Korb) exists on the GDC Vault but the free write-up contains no mechanism details (only that dialogue is fully voiced and arrives after deaths). — [Game Developer: Dive into the dialogue of Hades](https://www.gamedeveloper.com/audio/dive-into-the-dialogue-of-i-hades-i-at-gdc-2021); [GDC Vault entry](https://gdcvault.com/play/1026975/Breathing-Life-into-Greek-Myth)

**Firewatch (Campo Santo)**
- Radio conversation with Delilah: the player holds a button to pick a topic; "it's up to the player how much conversation is had at all"; Sean Vanaman: "We just sorta let the story expand and contract via player actions and choice as much as possible", and players "probably won't hear the majority of the stuff" but what they hear "will completely define your story". The article does not describe timers, silence handling or how Delilah initiates. — [GamesBeat: Firewatch crafts relationships through radio](https://gamesbeat.com/?p=114178)

### Inferences
- For a no-magic-strings codebase, Ruskin's design is the pattern: the *engine* knows only facts, criteria, rules, responses and expiring memory; every phrase (Hebrew/English) lives in the response data; "concept" names and fact keys are schema, not logic. A MapleSyrup "thought" = a response candidate produced by rules (or by the LLM) that must still pass director criteria (`intensity < X`, `seconds_since_last_utterance > N`, `player_not_speaking`, `not_in_menu`) before being voiced.
- The "re-query at callback time" trick is the cheapest robust way to drop a queued proactive utterance that became stale (e.g. the player entered combat while the thought was being generated).

### Gaps
- No primary source found giving numeric cooldowns for companion barks (Hades priority/cooldown rules, Firewatch timers, The Last of Us banter gating); the GDC Vault talks for Hades (2021) and The Last of Us buddy AI (2014) are paywalled/video-only, so only secondary summaries are available.


## Key Question 6 — Backchannels and fillers ("mm-hm", "wow"): effect on perceived naturalness and perceived latency; risks

### Takeaway
Controlled studies show natural spoken fillers ("Hmm, let's see…") significantly improve *perceived* response time, especially at long delays, while artificial wait indicators do not; but delays above ~4 s still degrade experience and prior robot work warns that simple fillers can reduce perceived intelligence. Backchannel *timing* is now predictable in real time from the user's acoustics (MAE ≈130 ms; VAP-based models label 500 ms ahead), but published Hebrew/English game-context evaluations do not exist.

### Cited Findings
- Maslych et al., CUI '25 (July 2025; arXiv 2507.22352): 54 participants, VR agents, 3 filler conditions (None; Artificial = rotating icon + processing sound; Natural = thinking gesture + spoken filler such as "Hmm, let's see…"/"Uhmmm…") × 3 delays (1.5 s, 4.0 s, 6.5 s). Delay had a large effect on perceived response time (ηp² = .422) and significant effects on engagement, impression, discomfort, competence and willingness to interact again; natural fillers significantly improved perceived response time (filler main effect ηp² = .081), especially at high delay, with a delay × filler interaction (p<.01) — but artificial indicators did not significantly improve any perception dimension, and fillers did not significantly change discomfort or willingness to interact again. The abstract states "latency above 4 seconds degrades quality of experience." The paper cites Jeong et al. 2019 as prior evidence that simple fillers can reduce a robot's perceived intelligence and likability. — [arXiv 2507.22352](https://arxiv.org/html/2507.22352v1)
- ElevenLabs' production "soft timeout" filler implements exactly this: default off, recommended 3.0 s, static text default "Hhmmmm...yeah.", optional LLM-generated contextual filler, once per turn, "avoid time references like 'one second'". — [ElevenLabs docs: Conversation flow](https://elevenlabs.io/docs/eleven-agents/customization/conversation-flow)
- Inoue et al., "Yeah, Un, Oh: Continuous and Real-time Backchannel Prediction" (arXiv 2410.15929): VAP transformer fine-tuned with a backchannel head predicts frame-wise backchannel timing and type (continuer "un/hai" vs assessment "he-/oh"); Japanese attentive-listening data (109 WoZ sessions with the android ERICA); positive frames labelled 500 ms before the actual backchannel; VAP bins 0–200/200–600/600–1200/1200–2000 ms; timing F1 42.85 (precision 32.5, recall 62.8) vs zero-shot VAP F1 15.1; continuer F1 38.1; no human evaluation reported in the text read. — [arXiv 2410.15929](https://arxiv.org/html/2410.15929v2)
- Paierl, Hagmüller & Schuppler, Interspeech 2025 ("Continuous prediction of backchannel timing for human-robot interaction"): regression models on continuously extracted acoustic features only, real-time capable; LightGBM best with mean absolute error ≈130 ms; strongest predictors are speaking duration, intensity and F0 in the window 275–875 ms before a backchannel. — [ISCA Archive: Paierl et al. 2025](https://www.isca-archive.org/interspeech_2025/paierl25_interspeech.html)
- Fukunaga et al., Interspeech 2025: predicting backchannel *surface form* (3- and 11-category) from general speaker/listener embeddings instead of personal IDs, +1.3 % / +0.9 % accuracy over ID embeddings; motivated by deployability in real systems. — [ISCA Archive: Fukunaga et al. 2025](https://www.isca-archive.org/interspeech_2025/fukunaga25_interspeech.html)
- Full-duplex models learn backchannels natively: PersonaPlex "learns timing behaviors: when to pause, interrupt, or backchannel (e.g., 'oh okay,' 'yeah')". — [NVIDIA Research: PersonaPlex](https://research.nvidia.com/labs/adlr/personaplex)

### Inferences
- For MapleSyrup's "let me think" hand-off to Claude, the evidence supports a *natural, content-bearing* filler (ideally generated from context, as ElevenLabs' LLM filler does) over a generic beep/icon, fired once, only when the predicted delay exceeds ~2–3 s, and never with time promises. Given the founder's no-magic-strings rule, filler phrases should be a per-language data table (as ElevenLabs' per-language overrides are).
- Backchannels while the *player* is talking are feasible with a ~130 ms-MAE acoustic predictor, but all published models are Japanese/English; for Hebrew the safe path is to backchannel only at clear prosodic/VAD pauses, keep them short, and allow the player to disable them — Jeong et al.'s finding that simple fillers can lower perceived intelligence is a real risk for a companion meant to feel smart.

### Gaps
- No study measuring the effect of fillers/backchannels on perceived latency *in a gaming context* or in Hebrew; Jeong et al. 2019 original paper not opened (cited via Maslych et al.).


## Key Question 7 — Estimating player intensity from observable game state (combat, HP, boss, travel, idle, menus) to gate speech

### Takeaway
Shipped games estimate "intensity"/"menace"/"immersion" with simple event-weighted accumulators that decay over time and are paused while threat is active (L4D), or with proximity/line-of-sight gauges (Alien: Isolation); academic work shows affect such as frustration can be predicted from gameplay telemetry alone (≈89 % pairwise accuracy from features like time standing still and death type), and the driving literature achieves F≈0.74 interruptibility prediction from 2-second sensor windows — all of which maps onto what MapleSyrup's vision engine can observe (HP/MP bars, damage numbers, mob count, boss HP bar, map name, portal/loading, menus, idle time).

### Cited Findings
- Left 4 Dead intensity model: per-Survivor Intensity increases with injury (scaled to damage), incapacitation, being pulled/pushed, and nearby Infected dying (inverse with distance); decays toward zero over time; decay is suspended while Infected actively engage the Survivor; the Director uses the max over players and cycles Build Up → Sustain Peak (3–5 s past peak) → Peak Fade → Relax (30–45 s or distance travelled). — [Booth 2009 slides (PDF)](https://steamcdn-a.akamaihd.net/apps/valve/2009/ai_systems_of_l4d_mike_booth.pdf)
- Alien: Isolation menace gauge: rises on proximity, line of sight and motion-tracker closeness; when it peaks the Director withdraws the threat to give relief. — [Game Developer: The Perfect Organism](https://www.gamedeveloper.com/design/the-perfect-organism-the-ai-of-alien-isolation)
- Pedersen, Togelius & Yannakakis (Super Mario Bros. player-experience modelling, ~2009): from gameplay logs (jumps, time standing still/running, items, deaths by type, kills) plus level parameters, a single-neuron model trained on pairwise preferences predicted frustration with 88.66 % accuracy (strongest features: time standing still +, time on last life −, jump difficulty −, share of gap deaths +), challenge 77.77 %, fun only 69.18 %; the authors call frustration "very well predicted". — [Pedersen et al. (PDF)](https://www.um.edu.mt/library/oar/bitstream/123456789/22955/1/Modeling_player_experience_in_Super_Mario_Bros.pdf)
- Driving analogue: interruptibility predicted from 1–5 s windows of vehicle/environment features with Random Forest F = 0.74 (2-s window). — [Kim et al. 2019 (PDF)](https://ic.kaist.ac.kr/files/papers/kim2019predicting.pdf)
- Industry patent practice: immersion estimated per player from game context (boss fight, weapon change), controller input and biometrics, with a threshold that depends on skill level and context, and user feedback used to retrain. — [USPTO 12,168,175](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/12168175)
- VR evidence that disruptiveness tracks engagement (rhythm game 5.56 vs loading 1.61) and that loading screens are the best-timed moments (6.51/7). — [Hsieh et al. CHI 2020](https://people.cs.nycu.edu.tw/~armuro/pubs/hsieh-et-al-2020-chi.pdf)
- Breakpoint theory: deferring to Medium/Coarse task boundaries lowers frustration; relevant content tolerated at finer breakpoints than general-interest content. — [Iqbal & Bailey CHI 2008](https://www.interruptions.net/literature/Iqbal-CHI08.pdf)

### Inferences (design sketch for a MapleSyrup "intensity" signal, derived from the above)
- Reuse the L4D shape: `intensity += w_event` for syrup-observable events (HP drop scaled by % lost; HP below alert threshold; death/tombstone; boss HP bar visible; many mob sprites/damage numbers per second; potion spam), `intensity *= decay` per tick, decay paused while damage numbers/mob contact continue. Keep all weights/thresholds in a data file (no magic constants in logic), per the founder's rule.
- Derive a small ordinal state from intensity + scene class: BOSS/COMBAT-PEAK (speak only for safety alerts, ≤1 short sentence), COMBAT (tips only if directly useful, no small talk), TRAVEL/GRIND-LULL (small talk allowed, cooldown-gated), TOWN/MENU/LOADING/IDLE (coarse breakpoint — best moment for initiative, opinions, humming), AFK (idle nudge after N seconds, like ElevenLabs `turn_timeout`/OpenAI `idle_timeout_ms`).
- Treat map transitions, portal/loading screens, "quest complete"/level-up banners, shop/inventory open, and return-to-town as **breakpoints** (Iqbal & Bailey's Medium/Coarse) that reset the proactive budget; treat the founder's example ("passing through Henesys on the way to Kerning") as TRAVEL — exactly the state where unsolicited small talk is welcome.
- **Cross-cutting synthesis for the "conversation director" (derived from all sections):** (1) one external policy decides *whether/when* to voice anything — the speech model only renders; (2) inputs: intensity state (above), breakpoint events, dialogue state (player speaking? companion speaking? seconds since last utterance), utterance class (safety alert / instruction / answer / small talk / humming) and its "relevance" value; (3) decision = Horvitz expected utility with class-specific thresholds that rise with intensity; (4) delivery through `response.create` (OpenAI) or `send_client_content` (Gemini) with the thought injected as context, after a *re-check* of the criteria at fire time (Ruskin's callback re-query) so stale thoughts die silently; (5) throttles = per-class cooldowns stored as expiring memory facts + random-chance criteria, both as data; (6) player-facing knobs = two scalars (initiative level, backchannel level) à la RESPOND; (7) measure: false-cutoff rate, unsolicited-utterance acceptance rate (player responds vs says "shh"), and latency from EOT to first audio.
- Like the patent, make the gating threshold a function of player skill/level and context, and let explicit player feedback ("not now", "shh") lower the proactivity scalar (RESPOND-style Turn-Claim-Aggressiveness knob) — Horvitz's "efficient termination" and "learning by observing" principles.
